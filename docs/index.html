hash-bait

Drop poisoned shortcuts on SMB shares to coerce NTLM hashes

I got tired of doing this in three tools — one to write the bait files, smbclient to push them, Responder to catch the hashes — and of picking bait out of client shares by hand afterwards. hash-bait is the whole errand as one static binary: it renders .url/.scf/.xml payloads, puts them on the share with its own SMB2/3 stack (no smbclient, no Python), starts Responder, and cleans up after itself. It assumes you have written authorization for the target and a Linux listener on the network. For authorized security testing only.

What's in it

Four subcommands cover the whole errand. Everything takes --dry-run to print the plan with no side effects, and every status line starts with a bracketed tag — [ok], [!], [x], [i] — so output stays meaningful piped or with NO_COLOR set.

  • Drop the baitdrop

    Renders @bait.url, @bait.scf and @bait.xml pointing at your callback address and writes them to the share over its own SMB2/3 stack. Starts Responder afterwards unless --no-listen. The leading @ sorts the files to the top of Explorer's view; -d targets a subdirectory when the share root is read-only.

  • Clean upclean

    Removes previously dropped bait, matched by basename, and warns about any file already gone. Leaving bait on a client's share is how engagements end badly.

  • Find the shareslist

    Enumerates shares on a target over IPC$ + srvsvc: one line per share, with its remark when the server gives one. Windows only for now — see known issues.

  • Catch the hasheslisten

    Starts Responder on an interface (Linux only) so the coerced authentications land somewhere. On any other platform it says so and exits 4.

  • Authenticated sessions-u

    -u svc-reader, -u LAB/svc-reader or -u svc-reader@LAB.LOCAL, with the password from $HASH_BAIT_PASSWORD or an --ask-pass prompt. No username at all tries a guest session — best-effort, see known issues.

  • Pick the payloads-p

    -p url,scf,xml (the default, all) or any subset, and --name changes the @bait basename when the default is burned. --save-local also writes copies in the current folder for inspection.

Tested on

Every check below runs on every commit; the pipeline is public in the repo. What hasn't been run says so.

  • Unit, golden and CLI testsPassed

    18 tests on the build host (Windows 11, stable Rust) and in CI on windows-2022 and ubuntu-24.04, with cargo fmt --check and clippy -D warnings. The golden tests pin the three payload bodies byte-for-byte against the original tool's output.

  • A live Windows share, in CIPassed

    The windows-2022 job creates a local user and share, then runs an authenticated drop, list and clean against 127.0.0.1, asserting the three bait files appear and the share is left empty.

  • A live Samba share, in CIPassed

    The ubuntu-24.04 job stands up Samba with a real user and asserts authenticated drop and clean. list and the anonymous drop run as informational probes — both fail today for crate reasons, below.

  • macOSNot run

    Cross-compiled for aarch64 and x86_64 on every release, unsigned and untested; probably works, no promises. First run needs xattr -d com.apple.quarantine on the binary.

Known issues

  • listen needs Responder, which only runs on Linux. On Windows it explains and exits 4; the usual split is drop --no-listen from anywhere, hash-bait listen on the Kali box.
  • Anonymous drops are guest sessions — the Rust SMB stack can't express a true null session, so guest + empty password is the portable equivalent. Against servers that accept the session before SSPI completes (Samba map to guest, most NAS devices) the smb crate errors with "SMB session setup succeeded before SSPI authentication completed" — a crate limitation, not fixable from here. Authenticated drops are the tested path; default Windows refuses guest either way.
  • list is Windows-only for now. Share enumeration binds DCE/RPC offering only the NDR64 transfer syntax; Windows accepts it, Samba's srvsvc endpoint rejects it. Until the crate learns classic NDR, list fails loudly against Samba and NAS targets while drop/clean work fine.
  • --pass is visible in the process list. Prefer --ask-pass or $HASH_BAIT_PASSWORD.
  • Nothing is signed. The Windows SmartScreen and macOS Gatekeeper warnings on first run are expected; SHA256SUMS.txt comes from the same release as the binaries it checks.
